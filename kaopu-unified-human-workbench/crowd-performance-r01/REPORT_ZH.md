# 人物整合性能初筛 R01

核验日期：2026-10-20。研究分支：`research/character-crowd-performance-r01-20261020`。本次提交只增加独立研究目录，原工作台与既有模型不变。

## 当前结论

**应先建立统一人物运行层，再进行完整多人容量测试。** 本轮已经执行原生衣物的 1／2／4 人 CPU 组件测试，并验证同款鞋跨人物共享资源。身体与密发使用另外的原生浏览器探针。完整的“最新身体＋最新头发结构＋衣服＋鞋＋多人＋全部物理”尚未实现，不能报支持人数或完整场景 FPS。

原因是各模块的现成接口和物理完成度不同：最新头发结构线的物理／密发后端仍锁定；鞋子是构建与几何弯曲工作台，没有独立力学求解器或穿脚适配；衣物运行器仍自己推进动作。把几个网页放在同一画面不会得到共用骨骼和碰撞状态的 NPC。

## 2. 衣物多人组件实测

原 MP05 R10 求解器，原保留试穿快照，104 骨骼／25,417 控制顶点，T03 上衣＋P02 下装、denim-bleach 参数、原生 `step` 动作。每个人持有独立求解世界，在一个 JS 线程顺序推进。Node 24.19.0，Intel Xeon Platinum 8573C，环境报告 9 个逻辑 CPU。

固定 `dt=1/60`，每个场景 60 步预热＋120 步采样；顺序为 1→2→4，再反向 4→2→1。下表为更新全部人物一遍的 CPU wall time，包括姿态、参考位置、求解和接触。

| 同时活动的独立人物衣物世界 | 第一轮均值／P95 | 第二轮均值／P95 |
|---|---:|---:|
| 1 | 16.09／18.98 ms | 16.12／19.91 ms |
| 2 | 33.69／39.57 ms | 33.27／41.17 ms |
| 4 | 68.38／78.55 ms | 75.15／115.71 ms |

原始 720 个采样值已由另一审查者重算。每人实际完成 180 步、3.000 秒模拟，无数值回滚、无安全暂停，最终坐标有限。四人逆序测试的抖动完整保留，没有只选择较快的一轮。

单人主要开销：细接触约 5.69–5.80 ms，下身碰撞 BVH 更新约 2.78 ms，参考位置更新约 2.11–2.25 ms，粗接触约 0.93–0.96 ms。细接触实际每步仅执行一轮，约 1,654 次查询，不是跑满源码中的最高循环次数。

**测量限制：** 这里跳过了发布工作台的 R07 重新分级和 GPU／WASM 联合 fit 初始化，没有渲染、头发、鞋、AI、空间场景或浏览器 Worker 并行。因此不能用 `1000 / 此表毫秒` 报 NPC 帧率。60 Hz 的整个更新周期只有 16.67 ms，这份结果提示衣物 CPU 路径需要优先优化，但不能据此保证任何用户机器的最终容量。

**质量没有自动通过：** 只在第 0、180 步做了密集接触采样；起点已有约 −3.095 mm 的层间距离，终点约 −4.744 mm，终点身体最小采样距离约 −0.250 mm；终点最大边长比约 1.583／2.036。首次发生问题的步数未知。由于省略了联合 fit，这些属于本组件试验条件，不能冒称发布 R07 网页的穿着缺陷。数值稳定和穿着质量必须分开检查。

复现：[cloth/REPRODUCE.md](cloth/REPRODUCE.md)。完整结果：[cloth/cloth-component-bench-r02.json](cloth/cloth-component-bench-r02.json)。

## 3. 已实现并验证的优化：同款鞋资源共享

新增 [shoe-sharing/shared-native-shoes.mjs](shoe-sharing/shared-native-shoes.mjs) 适配器。相同款式、尺寸、厚度、弯曲状态和材质配方只保留一份不可变几何，各鞋保留独立 Object3D 变换和生命周期。

实验使用 R14 原几何生成器、原 StyleMaterials 和实际解码的原纹理，四款鞋分别测试 1／4／8／16 人，每人两只鞋。基线尊重原工作台已经存在的左右鞋共享，新增收益来自跨人物共享。

| 16 人穿同款同尺寸鞋 | 原几何 ArrayBuffer | 共享后 | 减少 |
|---|---:|---:|---:|
| Penny | 60,479,104 B | 3,779,944 B | 93.75% |
| Chelsea | 68,439,424 B | 4,277,464 B | 93.75% |
| Monk | 59,335,040 B | 3,708,440 B | 93.75% |
| Canvas | 45,117,568 B | 2,819,848 B | 93.75% |

已核对顶点、法线、UV、索引、附加属性、材质组逐字节一致，原材质参数、生成的 shader 源码与回调一致，纹理引用可共享；没有做 GPU 编译或图像验证。修改一个人的左鞋位置和转动，不影响其右鞋或另一个人。原来源文件的哈希不变。

**93.75% 指 CPU 几何缓冲统计，不是总内存、显存或帧率。** 材质在主对照基线中本来已共用。三角形和绘制数量不变。不同尺寸、不同弯曲、不同配方要分别建资源；若需要逐人物 CPU 改写顶点，动态几何不能共用。

复现和证据见 [shoe-sharing/](shoe-sharing/)。这项优化尚未合入生产 NPC。

## 4. 头发与浏览器测量

F13 默认生成 114,171 根完整显示发丝，每根 48 段；每次头发绘制约 10,960,416 个三角形。物理实际上由 43×25＝1,075 个导向节点驱动，不能把显示发数等同于物理节点数。

路径纹理单份 89,522,176 B；F12 检查表示的相关数组按源码分配式核算约 217,267,413 B。这些是特定缓冲规模，不是实测总驻留量或整个应用总内存。运行角色可以按需创建检查用表示，同时保留显示发量；相同发型的静态路径也有跨人物共享机会，但两项尚未作为整合优化实测。

浏览器探针为原哈希验证后的 F13 增加只读取样入口和固定步长测试按钮。原工作台不变；每步仍沿用原动作、发丝物理、附件、相机、渲染和帧计数顺序，仅把用于诊断的 report/snapshot 放在计时前后。探针计量身体＋头发，明确没有衣物、鞋或多人。浏览器证据、实际 GPU 后端和样本完整性以 `BROWSER_EVIDENCE.json` 为准。GPU 指标是 Begin/End 命令之间的计时区间，可能包含 CPU 求解期间 GPU 等待提交的时间，不是 GPU 纯忙碌时间，不能单靠该指标判断 GPU 是主瓶颈。

本轮实际浏览器为 Windows／Chrome 155，ANGLE Direct3D11，**NVIDIA GeForce RTX 4070 Ti SUPER**；绘制缓冲 1425×1506，DPR 1.5。原生身体 266,098 显示顶点／531,702 三角，完整发丝 114,171 根。20 步预热＋120 步采样全部完成，正常速度行走、头发物理开启、无风；动作时钟与物理各推进 140 步，测量阶段实际推进 2.000 秒，错误数组为空。

| 身体＋头发单人，120 次原生更新 | 均值 | P95 |
|---|---:|---:|
| CPU 更新与渲染提交区间 | 78.69 ms | 119.30 ms |
| GPU 查询时间区间 | 32.37 ms | 84.77 ms |
| 全 pass 绘制调用 | 23 | 23 |
| 全 pass 提交三角形 | 13,714,940 | 13,714,940 |

GPU 120 个查询均取回、无 disjoint、无剩余查询。**帧调度异常仍未解释：** 119 个 rAF 间隔均值为 981.90 ms、P95 为 1067.70 ms；测量阶段 2 秒模拟耗时 116.918 秒。该间隔不能解释为显卡能力上限，不能据此宣布“约 1 FPS”，也不能用 CPU 与 GPU 两列相加计算 FPS。这是一次存在调度异常的原生更新成本采样，未通过持续实时运行验证。浏览器与衣物 CPU 测试来自不同环境，两边时间不能相加。

浏览器 JSON 保留统计摘要、环境和前后状态，没有保留逐帧时间数组；独立复核能核对样本数、时间推进和字段一致性，不能像衣物原始数组那样重新计算所有均值／P95。原生日志无错误且截图显示完整身体和发丝，只证明探针与原生内容实际运行，不构成穿着、美术、全部碰撞或多人质量验收。

## 5. 接下来应修改什么

1. **统一每个人的姿态输入。** 一个动作时钟、一个 finalPose、一个版本号。衣物、发根、鞋绑定读取相同结果，避免各自推进动作。原 MP05 `NativeMotion.evaluate(pose={}, matrices=null)` 的外部矩阵在第二参数，应为 `actor.evaluate({}, skinMatrices)`；还需要 Worker 通信适配，当前不能直接接进实时控制器。
2. **统一运行时资源与渲染通道。** 同一 THREE 工厂、renderer、scene；同一个 renderer 只安装一个 HairPassCache。各工作台 iframe 的对象计数器、模块级 singleton 和相机原点假设需要解除，不能把不同运行上下文的对象直接混入共享场景。鞋共享适配器提供了第一个实际例子。
3. **先消除重复计算，再分配连续预算。** 按 pose 版本更新共用身体碰撞输入，复用合法的最近面结果，避免重复网格构建／查询；不同接触模型和精度仍需分别维护。随后再按画面贡献、运动、接触和玩家交互的重要程度连续分配计算量，保持模拟时间正确，并以穿透、拉伸和画面误差约束调整。此处不新增动作缓存，不引入固定距离档位 LOD。
4. **完整人物接通后做真正的人群矩阵。** 同场景 1／2／4／8／16 人，行走／跑步／转身／接触；分别记录 CPU、GPU、所有 pass、峰值资源、模拟积压、质量误差，最后加入实际空间与 AI 成本。目标设备、分辨率、同时可见人数和衣物层数确定后，才能形成可用的容量结论。
