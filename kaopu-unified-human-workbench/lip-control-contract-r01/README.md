## 本轮解决什么

本轮只处理一个系统问题：**保存了参数、更新了 uniform，不足以证明当前画面使用了它。**

审核对象是主线冻结 R07，提交 `5543f756ca3af1428323696324303fa70b8de850`。`HeadSurface.js` 继承 ET19 的顶点处理，但用新的程序表面替换片元处理。旧嘴唇配方及控件仍存在，旧湿润片元的消费者却没有进入当前程序表面。

| 参数 | 原 ET19 材质的消费者 | R07 程序材质的消费者 |
|---|---|---|
| `lipStructure.wetness` | `uLWet` | 无 |
| `lipAnatomyDNA.upperWetness` | `uL19Wet.y` | 无 |
| `lipAnatomyDNA.lowerWetness` | `uL19Wet.x` | 无 |
| `proceduralHeadSurface.settings.lipWetness` | 保留为程序表面配方 | `psWet` |

基准源码：[HeadSurface.js](../human-integrated-r07/HeadSurface.js)、[LipOptics.mjs](../human-integrated-r06/specialists/lips-et19/LipOptics.mjs)。真实输出验证由独立文件 [verify-wetness.cjs](verify-wetness.cjs) 执行，不以产品的 `report()` 自述作为通过依据。

## 为什么选择这个改造

旧代码和新代码有相似名称，却有不同的参数含义和维度。ET19 将整体湿润量与上下唇各自的湿润量组合使用；R07 的 `psWet` 是另一套粗糙度和湿膜近似中的单一参数。没有经过校准，不能把上下唇取平均后声称完成了无损迁移。

本轮先让工作台如实表达当前支持的操作，保留原配方与原材质路径，再另行研究是否需要恢复上下唇独立材质能力。这个改造阻止无效实时编辑及误导性操作反馈；**它没有让嘴唇更逼真，也没有恢复程序材质中的上下唇独立湿润能力。**

## 实际行为

`LipControlContract.js` 在最终 R07 人物就绪后核对当前显示材质及已审查的挂接函数。

- 使用 R07 程序材质时，三个旧湿润输入保留原值，暂停编辑，并说明当前支持整体湿润；可直接进入真正有效的现有 `lipWetness` 输入。
- `lipWorkbench.set()`、`setDNA()` 及其底层入口，在发生不支持的湿润变更之前抛出 `LIP_CONTROL_INACTIVE`。混合修改整体拒绝；全量对象中未改变的旧字段不会误拦其他操作。
- 原“自然／偏干／湿润／重置”方案若包含不支持的湿润变化，在原处理器修改诊断状态、写入撤销历史之前被阻止。公开 `reset()` 具有同样保护。
- 切回已审查的原 ET19 材质，旧湿润控制重新可编辑。程序皮肤的配方单独保留。
- **导入和原唇部撤销属于配方恢复。** 它们继续恢复旧值和几何，不因原材质暂未显示就丢弃资料。撤销按钮及反馈明确说明，原唇部撤销不改变当前程序皮肤的湿润值。本轮没有新建第二套撤销历史。
- 未审查的材质对象或挂接函数不会被自动认作支持的消费者。诊断通道暂不显示湿润，与参数缺少消费者是两件不同的事。

原始 `headProceduralSkin.set()` 仍可准备未显示的程序表面配方。本合同没有拦截全部对象赋值或全部材质 API；它约束三个旧实时湿润编辑入口，并提供核对过的当前入口。

## 独立复核怎样改变了方案

第一次源码复核拒绝了四个遗漏：旧预设会在 setter 之前产生副作用；旧撤销绕过 setter；浏览器缓存恢复可能留下已卸载的保护；原材质分支对未知挂接缺少核对。

修订没有把旧撤销全部禁用，因为那会额外损害几何编辑。最终将它明确归为配方恢复例外，并增加“拒绝预设后，只撤销一次就必须恢复原几何”的独立回归，同时检查拒绝操作是否偷偷污染私有历史。

其余修订分别将预设拒绝前移到事件捕获阶段、保留浏览器缓存页面中的合同，以及核对原材质对象与挂接函数。缓存恢复的调整经过源码复核；本轮未单独声称已经完成真实浏览器往返缓存场景覆盖。

## 验证及否决标准

同一套冻结人物在实际 Chromium / SwiftShader 环境中进行比较，读取真实 WebGL 帧缓冲。嘴部范围来自原生 LipRails 在最终几何上的投影。

1. 如果被判为无效的旧控件已经产生真实嘴部响应，就否定本轮缺陷前提；如果原材质正对照不响应，则是证据无效、必要性尚未证明，不能反推缺陷不存在，也不能宣称候选通过。
2. 当前入口的低、高端必须逐字节等于原 R07 直接设置 `psWet` 的低、高端。原响应口外为零时，候选也必须严格为零；若原材质已有更宽响应，候选不能扩大响应且报告必须保留边界。
3. 人为构造“只有口外变化”和“在正确响应之外再改变一个口外像素”的反例，要求判据拒绝。此项检验检查器自身，不冒充人体实测。
4. 不操作时，候选与基准的人物参数、几何、相机、灯光及画面相同；无效混合操作原子拒绝。
5. 验证真实输入、原材质切换、非默认旧值的完整存档往返、原唇部撤销及当前值保留。
6. 仅在上述检查通过后发布独立候选，再读取固定提交的公开 HTTPS 页面，核对字节、启动及关键交互。

## 实际原版与候选对照

独立浏览器运行 [39091795794](https://github.com/haihao0307/guilin-dem-pipeline/actions/runs/39091795794) 在 2026-10-18 完成全部 14 项本地原版／候选检查。原始结果见 [evidence/local/qa.json](evidence/local/qa.json)。验证器作者另行解码 13 张 PNG，重算帧摘要及变化范围，与原 QA 一致。

| 问题 | 原版证据 | 候选证据与判断 |
|---|---|---|
| 旧整体、上唇、下唇湿润是否有效 | 参数接受 0→1，画面变化像素均为 0；真实 UI 也无响应 | R07 下暂停这些实时输入，API 在修改前拒绝；原值保留 |
| 测试是否看不见任何变化 | 相同上下唇参数切回原材质，分别改变 7,363 / 9,431 个区域内像素 | 候选切回原材质后复现相同数值，旧控制能力保留 |
| 当前有效入口是否接对 | 原 `psWet` 0→1 改变 47,502 个区域内像素，区域外 0 | 候选 API 与真实输入的低、高端帧分别与原有效入口完全相同 |
| 默认人物是否改变 | 冻结原人物的状态、几何、相机、灯光及实际帧 | 候选初始和全部操作后恢复的结果完全相同 |
| 旧配方与当前配方是否串改 | 二者属于不同材质模型 | 存档恢复 `.24 / .22 / .73` 三个旧值和 `.61` 当前值，状态、几何与画面精确恢复 |
| 拒绝操作是否污染撤销 | 旧预设处理器会先动诊断与历史 | 无效预设及 reset 在副作用前拒绝；一次原撤销恢复几何与旧配方，保留当前湿润值 |

数值来自 640×512 帧缓冲、固定默认人物与 macro 视角。独立区域是原生 LipRails 投影的保守矩形，x=66…574、y=61…434，外部仍有 137,314 个像素；它不是精确的唇红解剖分割。区域外零变化不能扩大解释为所有人物与视角的解剖或光学准确性。仅改外部全部像素及额外污染一个外部像素的两个人工判据反例均被拒绝。

## 保留理由与维护成本

保留依据是已经复现并阻断一种具体误导：状态写入成功，但当前输出不使用该字段。操作方直接得到当前能力边界，同时保留有效控制、配方和恢复路径。没有测量节省了多少工时，也没有据此宣称整套系统会自主成长。

这是冻结 R07 的适配层，依赖已审查的材质对象、挂接函数、控件选择器、旧预设值与写入口。上游改变后需要重审；未知材质即使可能有效，也不能被本层认定为已支持。R07 显示期间若要准备旧材质参数，需要切回原材质，或使用现有完整配方恢复路径；本轮没有新增“后台编辑未显示配方”的模式。

不应把这份包装脚本逐个复制到所有滑块。如果推广，控件、最终消费者和恢复语义应逐步来自共用定义，每一族仍保留独立输出反例。本轮证明的是一次局部纠错闭环及可重跑检查，尚未实现自动发现任意着色器消费关系或自主补全缺失能力。

## 构建与适用范围

构建在冻结 R07 HTML 末尾追加合同脚本。移除追加段必须逐字节还原宿主，全部原脚本摘要相同。没有重新构建或替换人物、着色器、灯光、预设和存档格式。继承原版远程资源加载器，不声称是离线文件。已验证候选为 5,462,383 字节，比原 HTML 增加 13,244 字节；这个体积差不是运行性能测试。

```bash
node kaopu-unified-human-workbench/lip-control-contract-r01/build.cjs
MODE=all \
BASELINE_PATH=kaopu-unified-human-workbench/human-integrated-r07/preview.html \
CANDIDATE_PATH=kaopu-unified-human-workbench/lip-control-contract-r01/preview.html \
QA_OUT=kaopu-unified-human-workbench/lip-control-contract-r01/evidence/local \
node kaopu-unified-human-workbench/lip-control-contract-r01/verify-wetness.cjs
```

需要 Node、Playwright `1.58.2`、pngjs `7.0.0` 和 Chromium。遇到新的宿主摘要会停止构建，要求重新审核兼容关系。首次仅覆盖冻结 R07 的三个旧湿润控制，不覆盖其他嘴唇色素、粗糙度、其他人物和其他专项分支。

本轮交付边界：实际修改生产源码；画面来自原实时三维工作台；没有生成图片替代；机器验证与用户审美验收分开；公开链接须先完成实际读回。离线打包与实体手机验收不在本轮已通过的声明内。
