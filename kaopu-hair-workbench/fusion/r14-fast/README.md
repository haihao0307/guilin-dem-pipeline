## 处理了什么

htmlpreview原实现先fetch完整HTML并res.text()，再document.write()。L01把原模型base64嵌入约21MB单文件，避免了第二次模型下载，却把等待前移到了整个网页取回之前。这不是理想的性能方案。

L02直接使用GitHub Pages版本目录。49,126字节HTML先显示界面，再加载5,741,226字节启动资源，合计5,790,352字节；相对L01的21,035,459字节，必要首开载荷减少72.47%。49KB只是入口，不是整个应用大小。

同源资源按512KiB以内分块，4并发、最多3次重试，完整SHA-256校验后缓存。缓存不可用或空间不足时仍读取同一质量网络数据；不自动降画质、不清理其他工作台缓存、不注册全站Service Worker。损坏缓存和首个请求503的故障注入已验证：只重下损坏的524,288字节块，其余14块复用。

原GNM按完整section无损分割。首开保留精确模板、三角形、四边形、权重、标志、关节与landmark。毛发工作台当前未调用的identity_basis/expression_basis按需加载，不删除数据。await lengthGroom.loadOriginalBases()可恢复并验证原始34,937,952字节整包SHA：fd19f46eef6f8bfb725fceab581e1bc8837209997ca3fd43f3c1735003c86961。基底未加载时明确阻止相应编辑方法，不用缺失数据或简化头模替代。

导向查找采用精确分支定界树，保留原距离函数、兼容性、权重和等距索引次序；不是近似查找、LOD或减少发丝。

## 时间对照与必须保留的异常

受控同机对照采用5Mbps/80ms、Chromium140与SwiftShader。旧L01使用整页下载方式重放，不是用户现场抓包。首次绘制34.056秒→0.144秒，全质量就绪100.214秒→68.9477秒，约缩短31.2%。这些软件渲染绝对秒数不是用户显卡的承诺。

独立原生公网冷启动：首次绘制0.276秒，全部启动资源9.4541秒就绪，全质量模型68.4168秒就绪。

**公网刷新存在尚未解决的额外等待：**虽然全部15个启动块命中缓存、资源网络下载为0，加载器到49.2228秒才开始运行，首次绘制49.240秒，全质量就绪106.9003秒。加载器运行前的这段延迟尚未独立定位；不能只凭此报告确定为网络、显卡回收或测试导航流程。不能拿候选本地刷新约0.273秒资源就绪的结果，声称公网刷新总耗时一定更短。缓存命中只证明没有重下资产，不等于场景重建或刷新没有成本。

本轮明确改善的是首开传输、界面白屏屏障及导向计算；刷新进入阶段仍需单独剖析。默认约201MB发丝几何不减量，CPU、GPU、驱动和多窗口资源压力仍影响总用时。原冠部起翘/露皮等视觉缺陷未变，本轮没有新增物理。
