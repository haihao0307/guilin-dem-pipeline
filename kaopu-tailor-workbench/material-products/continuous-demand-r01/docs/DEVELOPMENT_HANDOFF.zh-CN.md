## 0. 开工指令

在 MP05-R2 的独立候选中优化实时服装物理，保留用户认可的真实针织结构、材料效果、裁片、缝合、厚度、人物与既有灯光。先测量并优化已有 WASM / Worker / 数据传递链路，再建立连续需求函数，分别调度物理额外求解、几何生成、资源驻留与上传。

禁止以固定距离的 LOD0/1/2、整件高低模切换、删除针目、把真实编织替换成一张普通贴图、关闭碰撞、冻结物理、放慢模拟时间、播放预录布料动作来完成指标。本轮不开发动作缓存；旧版已有缓存保留在旧入口中，不作为新实时方案的依赖或成绩。

“无级”指需求、误差目标与视觉过渡连续，不是声称计算机能够提交小数个三角形或在零时间内载入无限细节。执行端必须同时报告真实画面流畅度、物理时间推进速度、碰撞质量与资源开销。

完成一个阶段就提交该阶段的独立证据；不可把“物理链路优化完成”写成“连续几何系统全部完成”。最终交付必须有可外部打开的固定 HTTPS 网页、源码提交、测试环境和证据，旧版保留，Draft PR 不自动合并、不强推。

## 2. 先修正此前的架构判断

当前不是“只有贴图，没有编织”，也不是“没有 Shader，需要从零加入”。`solid-textiles.mjs` 已有闭合管状纱线、实例化、材质着色器定制及与纱线形变一致的深度材质；`surface-binding.mjs` 已将裁片控制位置、法线、UV 放入控制纹理，通过顶点着色器驱动纱线。[G02][G03]

当前也不是“每根纱线都作为物理自由度”。`CoupledCloth` 从服装裁片数据建立 `ClothSolver`，随后由 WASM 后端推进；外观纱线通过表面绑定跟随。代理 / 宏观控制面驱动细节这一方向已经存在，不能重新建一个重复的物理世界。[G04][G05]

`cloth-controller.mjs` 已使用 Worker，`cloth-worker.mjs` 已使用可转移缓冲区，`wasm-cloth.mjs` 已使用 WASM；“加一个 Worker / 加 WASM / 加 Transferable”不是本轮的新优化。[G05][G06][G07]

此前“针目物理导致指数增长”“换 GPU 一定快几十倍”的说法没有得到这个版本源码与实测支持，应撤回。这里应测量实际自由度、约束数量、迭代、候选碰撞对、内存复制、GPU 提交和同步成本，而不是从外观复杂度推断物理复杂度。

### 2.1 代码里已经存在的两种路径，必须分开测试

`FastClothController.playMotion()` 主要使用已验证物理帧回放；`play()`、`settle()`、`tug()` 等可进入 live reference solver。源码审计接口明确写了 `liveClothRealtimeCertified:false`。[G08]

因此，“已有动作播放很快”不能证明“任意受力、任意接触下实时物理很快”。新候选应单独暴露 `physicsSource=live` 的测试入口，避免默认回放路径混入性能验收。原有动作数据可以作为人体姿态输入；不能把已经算好的衣服顶点序列作为求解结果。

### 2.2 当前显示链路也并非始终只画真实纱线

`adaptive-solid.mjs` 普通视图使用有限厚度的聚合曲面，显微视图异步构建原生纱线，并通过 `detail(true/false)` 切换可见对象。`solid-textiles.mjs` 内部另有三档离散几何 / 材质，距离判断为 `dist < .21 ? 2 : dist < .48 ? 1 : 0`，不同档位还可能改变股线表示。[G09][G02]

这说明用户要求的“不要固定分档、不要整件突变”确实对应现有待改代码，不是仅调整界面名称。旧实现可以作为冻结的对照组；最终新调度路径不得继续隐藏调用这些距离分档来冒充连续方案。

## 3. 目标架构：不重做材料，不重复物理，用同一份状态驱动

```text
服装定义：裁片 / 缝合 / 材料参数 / 编织路径 / 稳定随机种子
                  │
                  ▼
持久的宏观服装状态：位置、速度、约束状态、接触记录、时间戳
                  │
         现有 WASM 求解器，逐步优化
                  │
           小型控制面位置与法线
                  │
         现有表面绑定 + 顶点着色器
                  │
      同一程序化纱线结构 + 同一材料外观

连续需求函数 ──► 额外求解优先级 / 生成任务 / 驻留 / 上传 / 可见细节采样
安全规则     ──► 必要约束、接触、时间推进，不受远近和遮挡取消
```

物理状态的身份与生命周期不能由摄像机距离决定。离远、转身、暂时遮挡、卸载外观细节，都不得重置服装位置、速度或模拟时间；重新需要细节时，绑定当前状态，而不是从初始静止状态重新播放。

针目、纱线走向、股线、颜色与拓扑属于同一个材料定义。需要改变的是“为了当前屏幕误差允许多少数值采样、何时生成哪些数据”，不是“远处换另一件衣服”。

本轮保留宏观物理拓扑，避免把动态重网格、跨分辨率物理状态迁移也塞进性能优化。后者会引入质量、动量、接触和约束状态转移问题，本轮没有必要承担这项额外风险。

## 4. 先做可以直接定位的优化，而不是先换渲染器

### 4.1 第一优先：消除重复结果整理与静态数据传输

已读调用链：`wasm-cloth.mjs` 中的 step 实现返回 `w.rows()`；Worker 的 `step` 分支忽略该返回值，然后 `send()` 又调用一次 `world.rows()`。而 `rows()` 会复制位置、法线，生成审计信息，并重新拼装静态三角形索引。[G04][G05][G06]

改动要求：一次输出只整理一次结果。可以让 `step()` 只推进状态、`writeSnapshot(target)` 负责输出；或者让调用者复用该次返回值，二选一，不得两次都保留。初始化时一次性发送拓扑索引、面板映射与不变 orientation，逐帧只传动态字段及 revision。

建议为位置、法线、回滚快照和输出缓冲区建立有上限的复用池。当前已经用了 Transferable，所以重点是减少新分配与重复复制，而不是换一个传输名词。必须明确发送、接收、归还的所有权；不能转移仍在求解的 WASM 活跃内存，也不能在 buffer 已被转移后继续读写。

保留数值回滚安全能力，但把每步 `slice()` 创建回滚快照改为预分配内存写入。出现失败时必须恢复本次事务涉及的状态，不仅是位置，还包括速度、模拟时间、人体姿态 / 碰撞更新状态以及相关缓存有效性。[G06]

### 4.2 第二优先：不动的数据不重复更新

Worker 当前每次输出都会建立人体数组。主线程服装更新还会复制数据、重算包围体、更新表面绑定；人体同步链路也存在法线与包围体更新。[G05][G10][G11]

增加 `bodyRevision`、`clothRevision`、`topologyRevision`、`materialRevision`。人体姿态不变时不重新发送完整人体、不重新计算它的全部法线；布料仍然继续求解。服装真的变化才更新对应显示状态。换颜色、灯光或摄像机，不应重置物理或重建裁片绑定。

这不是“看不见就不算物理”：省略的是未变化的数据整理与重复显示更新，不是跳过必要状态推进。

### 4.3 第三优先：隐藏外观分支不要重复做显示工作

`adaptive-solid.deform()` 会更新聚合曲面、边缘和饰边，再在显微模式更新真实纱线。先核对哪些隐藏分支的 CPU 工作仍是必要的，哪些只为显示服务。[G09]

可以停止隐藏显示对象的重复顶点拷贝与法线处理，但必须保留权威控制面和碰撞数据。重新显示时，从最新 revision 一次重建显示状态，不能恢复旧形态。对真实纱线主路径，不要破坏现有控制纹理 / 顶点绑定方式去改成逐帧 CPU 重建全部纱线。

### 4.4 第四优先：时钟与显示提交分离

`ClothController.play()` 当前在一次 `step` 返回后，再等待 `setTimeout(next,10)`；Worker 每个 `step` 推进固定 `1/60` 秒。[G07][G05]

改为基于单调时钟的固定步长推进：记录真实经过时间、累计未推进时间、完整物理步数和最近结果年龄。第一轮先保持现有物理步长 / 子步语义，不与迭代策略同时改动。调度器可以合并或丢弃已经过时的“显示快照”，不能为了显示流畅随意丢弃物理时间或交互事件。

主线程采用有限长度结果队列 / 最新完整快照邮箱；Worker 不必为每个中间结果都创建完整显示快照。但共享状态与输入事件的时序必须可追踪，不能把未来人体姿态配上过去布料位置。

必要时在两个已完成状态之间做显示插值。这只是数值显示插值，不是动作缓存；同时要检查插值画面中的接触、缝合与人体同步。普通位置插值不自动保证不穿模，不能省掉这项检查。

若算力不足，报告 `overBudget`、`simLagMs` 与失效场景，继续排查瓶颈。禁止通过不断清空累计时间、降低真实播放速度、重复旧状态来达成虚假的 60 FPS。

## 5. 连续需求函数：距离只是输入之一

以下是建议接口与初始函数族，不是已经在 MP05 上标定的参数。开发端应能在诊断面板显示每个输入、函数输出与实际分配的工作量。

### 5.1 两种距离，不能混为一谈

`dHero` 是服装区域与主角交互位置 / 身体包围体的距离，用于交互优先级和预取。`zCamera` 是摄像机空间深度，用于估计屏幕可分辨细节。

主角自己的衣服通常始终 `dHero≈0`。如果只看它，拉近摄像机、改变焦距、进入显微视图都无法得到正确的细节需求。远离主角但被长焦镜头放大的物体，也可能仍需高显示精度。

### 5.2 视觉需求

```text
D = 1 / (1 + (dHero / d0)^2)
S = 1 - exp(-(featurePixels / s0)^2)
I = 1 - (1 - wd*D) * (1 - ws*S) * (1 - wf*focus)
qVisualTarget = qMin + (1 - qMin) * visibilityDemand * I
```

`wd/ws/wf`、`focus`、`visibilityDemand` 在 `[0,1]`；`d0>0` 和 `s0>0` 是曲线尺度，不是切换阈值；`qMin` 是可选任务的最低分配偏好，不代表物理安全下限。必须限制所有输入的有效范围并处理 NaN、零视口与近裁切面情况。

`featurePixels` 表示指定纱线 / 针目 / 误差范围投影到画面的尺寸，不应只用整件衣服的包围盒面积。在透视相机的小范围近似下，可用 `fPixels * featureMeters / zCamera`；倾斜区域和正交相机使用实际投影或投影导数。分辨率、DPR、焦距、屏幕边缘、轮廓和阴影需求也要进入实际实现。

`visibilityDemand` 用于外观和预取，不用于关闭接触。需要考虑光源视角：摄像机看不见、但仍向画面投影的衣服区域，仍可能需要阴影几何。

### 5.3 时间平滑

```text
qNext = qCurrent + (1 - exp(-deltaSeconds / tau))
                    * (qTarget - qCurrent)
```

正常情况采用“需求上升快、下降慢”。例如上升 `tau=0.10s`、下降 `tau=0.50s` 可以作为实验起点，必须标注为待测参数。稳定的资源驻留宽限时间也可避免来回生成；这是防抖，不是另造距离档位。

紧急接触、抓取、突然暴露的关键轮廓属于安全 / 可见性事件，不能为追求数学上的平滑而延迟必要处理。日常需求连续变化，与安全事件即时响应可以同时存在。

### 5.4 物理额外工作需求

```text
E = normalizedResidual / (1 + normalizedResidual)
qPhysicsExtra = 1 - (1 - qVisual) * (1 - E) * (1 - contactRisk)
```

残差和接触风险都必须来自实际物理状态：约束未收敛程度、相对接近速度、间距、扫掠包围体、接触变化等。碰撞迫近时，安全任务直接获得强制处理资格，不能只靠一个浮点权重与普通加载任务竞争。

`qPhysicsExtra` 决定额外校正的优先级，**不得直接乘到重力、质量、弹性、阻尼、碰撞厚度或时间步长上**。材料不会因为摄像机远离而改变属性。主角近处优先更充分收敛；远处仍满足统一的安全和形变误差底线。

### 5.5 “连续预算”如何变成实际工作

把工作拆成有界任务，记录估计成本。一个示例优先级为：

```text
priority(task) = importance(task) * expectedErrorReduction(task)
                 / max(estimatedCost(task), costFloor)
```

先执行当前时间区间所需的安全与基础求解，再分配剩余预算给额外校正、细节生成和上传。任务数量必然是整数，预算和优先级可以连续变化；不得用三档 quality 枚举替代这个过程。

CPU 主线程、Worker、GPU、内存和网络是不同资源池，不共用一个不分单位的预算数值。耗时预测要平滑、限速，且允许任务最小粒度和饥饿保护；不能每一帧按瞬时 FPS 大幅增减负载，造成“越卡越乱”的调度振荡。

## 6. 实时求解器：按误差减少重复处理，不按远近取消物理

### 6.1 已读到的重路径

`wasm-cloth.mjs` 中，默认 `dt=1/60` 时，`ceil(dt*240)` 得到 4 个子步。每个子步有 16 轮主要约束处理、12 轮额外应变 / 接触处理，以及后续的接触修正与密集采样。多轮中会调用人体投影、上下衣物互碰撞和包围层次更新。[G06]

这是源码里的执行结构，不是测得的耗时占比；不能仅凭轮数就断言哪个函数一定最慢。

### 6.2 第一阶段保持方程和结果，测清楚成本

在现有循环上加低开销分段计时和计数，至少区分：预测、拉伸约束、弯曲、应变限制、人体接触、衣物互碰、密集采样、BVH 更新、法线 / 输出展开、安全审计、结果整理。

先完成第 4 节的重复工作消除，保持原有数值循环作为参考。这样能区分“把同样计算组织得更好”与“少算导致近似结果变化”。

### 6.3 第二阶段才引入收敛停止与活动区域

为每类约束定义有单位、可解释的残差。对不含约束阻尼项的弹性 XPBD 等式约束，参考形式为：

```text
alphaTilde = compliance / h^2
elasticResidual_j = abs(C_j(x) + alphaTilde_j * lambda_j)
```

上式是对应等式的局部残差，不是所有接触与整套耦合系统的统一停止条件。弹性衣物允许有物理伸长，不能把 `C_j(x)=0` 当作一切材料都应达到的目标。现有 C/WASM 中所有约束需要逐类审查；不能因为出现 lambda 和 h² 就宣称整个求解器已满足完整 XPBD 收敛性质。[R01]

单边接触要单独检查非穿透、接触激活及相应约束条件；应变界限、缝合误差与速度异常也单独评估。新增一次接触校正可能重新破坏其他约束，因此必须在耦合处理后重新检查，而不是某个局部残差低就永远跳过该区域。

早停仅在统一安全门槛和基础误差门槛全部满足后允许。额外视觉精度可以按连续需求分配，但不能拿“远处看不出来”作为穿模、接触失效、衣服持续变长的理由。

不要直接把 16 轮改成 4 轮、12 轮改成 2 轮，然后仅看 FPS。先做受控比较，记录误差随迭代的曲线和真正减少了多少重复工作。小子步与多迭代如何取舍值得参考研究，但论文示例的结果不能替代本工作台的碰撞测试。[R02]

### 6.4 以物理状态决定活动区域

袖口、下摆不天然等于高成本区，胸背也不天然可以少算。应根据残差、变形变化、接触、抓取、相邻区域受力来决定哪里需要额外求解。

宏观状态共享、缝合顶点共享；分区之间保留邻接传播与边界协同处理。区域的邻域范围必须覆盖实际依赖，不能固定一个“一圈顶点”就假定充分。不能把衣服分成互不耦合的小布片，各自求解后仅在显示上拼起来。

低活动区域仍保留其质量、约束、速度及必要接触。没有外部变化且达到平衡时可以避免重复的可选计算；一旦相邻受力、人体移动或接触改变，应及时恢复需要的处理。这里不采用“离远即冻结”的方案。

### 6.5 碰撞优化的保守边界

现有实现已有最近面缓存、BVH 与静态 SDF，先复用而非重复开发。[G04][G06]

可以优化候选生成、接触记录有效性、空间划分和确实不变的 BVH 节点更新。减少远离接触区的昂贵精检前，必须证明当前时间区间内不会漏掉相交候选，例如使用保守的扫掠包围体；不能用相机距离或上帧“没碰到”代替这个证明。

当顶点改变时，缓存法线、最近面和包围体都可能失效。开发端要明确每个缓存的失效条件，不能为提速继续使用不再包住几何的旧边界。

现有审计记录 `continuousCollision=false`、`allSelfCollision=false`。本轮不能通过减少采样进一步恶化，再宣称“完全不穿模”。对快速运动、厚布、交叉手臂和内外层挤压应建立专项测试；需要补充 CCD 或自碰撞时独立记录新增成本与范围。[G04]

## 7. 按需加载：数据何时存在，与物理是否存在分开

### 7.1 始终保留的轻量内容

服装身份、裁片 / 缝合定义、材料参数、程序化编织规则、稳定种子、宏观物理状态、必要碰撞状态与边界关系。卸载高精外观数据，不得卸载仍影响主角 / 相邻物体的必要物理状态。

本轮不做整个世界的无限角色管理。对当前工作台里的衣物，优先保留完整宏观状态；未来加入大量角色时，另行定义生命周期，不在此悄悄改成停算。

### 7.2 按需生成或驻留的较重内容

局部纱线细节的采样数据、GPU 顶点 / 索引页、局部辅助显示数据及需要时才用到的高精诊断资源。程序化项目的“加载”不一定从网络下载网格，也可能是按需求生成并上传数据。

状态机建议：

```text
有规则描述 → 排队 → CPU 生成 / 读取 → GPU 上传 → 可安全提交
                                    ↓
                         过时取消或资源回收
```

给任务带上服装身份、拓扑 revision、材料 revision、请求 generation。切换款式后过时任务不得把旧结果写回新衣服。任务失败保留最近有效显示结果，报告细节尚未就绪；不能留下黑块或整片缺口。

### 7.3 预取而不是等到镜头贴上才工作

结合主角和摄像机的速度、转向、焦距变化，预测短期可能需要的区域。预取窗口至少考虑生成、解压、网络、上传与着色器准备时间；窗口大小必须由测量和内存预算决定，不写死“某个距离就是高精”。

采用小块任务、有限并发与每帧上传上限。不能把同一帧里的几十个细节任务同时完成后一次上传，造成“整体平均帧率提高，但靠近瞬间卡死”。

远离后延迟回收，优先回收不再必要的细节；关键轮廓、当前可见覆盖和可能影响当前阴影的资源要保留。在资源压力下先取消过时请求，避免同一块反复创建和销毁。

### 7.4 必须承认的性能边界

如果一块完整高精几何已经驻留并且仍然全部绘制，只调整加载优先级不会减少它每帧的顶点着色和三角形提交成本。如果本轮慢在实时碰撞，也不能靠卸载贴图解决。

所以按需加载主要解决启动、峰值内存、生成 / 上传突刺和不必要的驻留；物理链路和可见几何采样分别处理。不能把任何一个机制称作其他两个问题的自动解法。

## 8. 无级外观：同一编织定义，连续误差目标，不准备三套衣服

此节替换旧距离档位，属于独立的显示改造。必须与第 4～6 节分别测量，不能让一次大重写遮住实时物理优化是否有效。

### 8.1 保留的身份

保留针目数、线圈连接、纱线中心路径、物理尺度、真实厚度、股线定义、花纹相位和随机种子。近远观察看到的都是同一件衣服。针织正反面、收边与缝线也使用相同身份和控制面，不得重新随机生成。

禁止旧有 `dist<.21/.48` 档位选择，禁止以独立壳面和真纱线整件互换作为新方案。若显微镜按钮保留，它只改变观察需求 / 精度上限，不更换服装身份或重启物理。

### 8.2 连续控制的是屏幕误差，不是“高 / 中 / 低”标签

```text
epsilonPixels(q) = epsilonStrict
                 + (epsilonLoose - epsilonStrict) * (1 - q)^gamma
```

例如 `epsilonStrict=0.25 px`、`epsilonLoose=0.75 px`、`gamma=2` 仅可作为实验起点；这不是已通过验收的通用阈值。轮廓、缝线、针孔和明暗变化明显的位置可能需要更严格的约束，多个误差来源不能各自都用满同一总误差预算。

根据同一条程序化纱线在当前视角下的投影误差，决定哪里增加或减少采样，而不是切换预制高低模型。可以使用曲线中点 / 四分点相对弦线的投影偏离、切线变化、截面轮廓误差等作为估计。采样估计不是严格全局上界，必须通过密集参考对照检查漏判。

对投影近似为圆的管截面，规则 n 边形的径向弦误差可由 `radiusPixels*(1-cos(pi/n))` 估计；斜视、透视与变形截面应以实际投影为准，不能直接套成全场保证。采样最小数量还必须保留每个针目 / 弯折 / 交叉结构，不能因一个误差估计低就把线圈拉成直线。

严格说，这属于连续自适应细节管理，仍然在管理计算复杂度；它不是“从此没有任何离散化”。本方案拒绝的是固定距离档位、预制整件替换与明显跳变，不把已有术语换个名字就称为新算法。

### 8.3 拓扑采样变化要有稳定过渡

同一局部片块可以保留稳定的参数域地址及嵌套采样关系。增加采样时，新顶点先位于旧近似曲面，再以连续权重靠近同一真实曲线的采样位置；减少采样时反向处理，完成后再释放不必要索引和顶点。过渡两端都从当前控制面重新求值，不能将某一端锁在过时的人体或衣服姿态上。

相邻片块共享边界参数与过渡状态。管截面、段端封口、裁片边缘和缝合处不得产生裂缝；真实纱线的连接和穿绕顺序不得改变。过渡期间允许少量临时资源，但应有峰值预算，不能常态同时渲染两整件衣服。

此方法是待验证的工程方案，不保证任意编织都能直接套用。跨股线、封口、扭转法线与边界的采样适配是本节的重要工作量。无法通过视觉和结构测试时，保留同一真纱线的固定合格采样，先交付物理链路收益，明确连续采样尚未完成。

### 8.4 亚像素细节不能用消失来解决闪烁

使用与当前针织定义一致的覆盖、法线 / 光照过滤，维持平均颜色、粗糙感与遮蔽趋势。不能通过把线径变细、删除一半针目、突然变单股、添加不透明底板来减少开销。滤波不是改写材料或织法。

几何位移、法线、主渲染与阴影通道应使用一致的采样 / 过渡状态；否则衣服不跳，影子仍会跳。遮挡剔除也要覆盖当前帧的真实变形边界。

当前 `solid-textiles.mjs` 在 `moving` 时绕过片块视锥剔除，是为了避免使用失效的静态包围体。不能直接删除 `moving ||` 来追求速度；先建立由当前控制面驱动的保守世界空间边界，并加入厚度与所需运动余量，再分别对摄像机和光源判断。[G02]

### 8.5 两个不得混淆的完成状态

“分块加载 / 固定真纱线采样”可以先完成，保留现有效果，但它不保证降低所有可见纱线的绘制成本。

“同一真纱线的连续误差控制采样”是进一步减少可见几何成本的方案，必须独立通过无跳变、无裂缝、纹理相位一致和远景稳定测试。不能仅把 shader 中的质量权重改为浮点数，就声称完成了几何复杂度优化；若仍提交相同顶点，顶点成本并没有因此消失。

## 9. Compute Shader 的位置：可选后端，不是第一步救火

当前 `person/Viewer.mjs` 实际创建的是 `THREE.WebGLRenderer`。真实纱线材质依赖 `onBeforeCompile` 与自定义深度材质。[G11][G02]

Three.js 官方说明，`WebGPURenderer` 不直接支持现有 `ShaderMaterial` / `RawShaderMaterial` / `onBeforeCompile` 这类自定义路径，需要迁移至节点材质与 TSL。因此不能把更换渲染器当成一行配置、也不能假定普通材质能自动保住当前针织效果。[R03]

建议第一轮保留 WASM + WebGL，把实测热点解决，再决定是否投入端到端 GPU 物理后端。目标链路应该是：GPU 上的宏观状态 → GPU 上的约束与接触 → 同一设备上的显示绑定与渲染消费。避免 GPU 计算后逐帧全量读回 CPU，再上传给独立 WebGL 上下文的往返路径；它不能视为零拷贝共享。[R04]

GPU 后端需单独解决：共享顶点约束的并行写冲突、确定性 / 约束顺序、接触候选与溢出、浮点精度差异、正常数值范围、资源生命周期和设备丢失恢复。WGSL 的可用数值类型及同步模型与当前 Float64Array / WASM 链路不同，不能未经校验逐项翻译后宣称等效。[R05]

约束并行可研究图着色后分批、或 Jacobi 型分离写入 / 汇总方案；不同收敛行为要与现有参考解对照。复杂碰撞下 GPU 并不一定比已优化 CPU/WASM 更快，是否迁移由完整链路测量决定，不以技术名称决定。

WebGPU 不可用时保留已验证的 WASM 路径，并在诊断中标明实际后端，不把渲染回退误报为 GPU 物理仍在运行。SharedArrayBuffer 等机制也不是本方案前提；依赖它时应先验证当前托管环境的隔离条件，不能让交付卡在未经验证的服务器配置上。[R04][R06]

## 11. 分阶段执行与每阶段出口

| 阶段 | 范围 | 必交付物 | 不允许冒充的成果 |
|---|---|---|---|
| S0：实测基线 | 锁定源码、识别 live 与回放、记录真实链路 | 基线清单、trace、硬件 / 浏览器 / 视口、热点占比 | 不能凭旧 README 的播放帧率判定实时物理 |
| S1：实时管线减负 | 单次结果整理、静态数据分离、buffer 复用、revision、时钟 | 独立候选、逐项开关、同一输入前后测量 | 不声称连续几何或 GPU 物理已完成 |
| S2：安全自适应求解 | 逐类残差、接触候选、耦合早停、额外工作调度 | 误差与成本曲线、安全失败回退证据 | 不靠距离缩小碰撞 / 改材料属性 |
| S3：连续按需外观 | 同一定义分块、生成上传预算、替换距离档位、连续采样 | 相机往返视频、资源轨迹、轮廓与阴影对照 | 不用三套预制衣服和整件切换冒充 |
| S4：GPU 可行性验证 | 仅在热点与预期净收益支持时启动 | 小范围端到端原型、材质一致性、真实净收益 | 不把 WebGPU 构造成功当物理优化完成 |

S0～S3 是本方法的主要开发路线。S4 不是前面阶段的开工前提，也不是自动获准替换六个工作台的渲染器。外观优化与实时物理优化分别统计，然后再合成整页成绩。

建议先以用户给出的 K04 上下针织组合为首个样本，再做皮革 + 牛仔回归；不能只针对单材质快速路径优化后把其他服装改坏。保留原缩略图、款式与参数入口。存在新的用户已认可主线时，应在接手确认后做差异迁移，不覆盖其他窗口的活动分支。

## 12. 验收：既看得顺，也算得对

### 12.1 测试条件必须记录

记录 CPU、GPU、内存、操作系统、浏览器版本、渲染后端、视口、DPR、阴影设置、材质参数、服装组合、物理自由度、输入序列、源码 SHA 和首次 / 热启动状态。手机视口不等于手机实机，软件渲染不等于用户显卡。

建议每个条件先预热，再做至少 60 秒的重复测试，至少重复三次；冷启动单列。统计 p50 / p95 / p99 和峰值，不只报平均 FPS。记录温升或后台任务干扰，不在不同画质、不同物理时间或不同硬件上直接计算加速比。

### 12.2 必测情形

| 场景 | 核心检查 |
|---|---|
| 静止人体上的实时重力、抓取后松手 | 布料仍在 live 求解；结果返回无重复静态数据；UI 可操作 |
| 连续改变风 / 外力 / 合法物理参数 | 非预录动作输入仍能响应；不重新烘焙整段动画 |
| 后续接人体运动时的抬手、转身、下蹲 / 挤压 | 布料与人体时间一致；接触不漏；不是衣服缓存回放 |
| 拉近—拉远—横移—转背—快速回头 | 无固定距离台阶，无编织相位重置，无明显载入空洞 |
| 背光、轮廓、阴影、内外侧与缝合处 | 细节采样变化不产生闪烁、断线、裂缝和影子跳变 |
| 频繁切换款式 / 材质、取消未完成生成 | 旧请求不污染新衣物，内存无持续增长 |
| 连续开物理、内存压力与图形上下文恢复 | 状态与资源生命周期有界，失败可解释，不静默退回假物理 |

人体动作接入还未完成时，可以先使用受控运动碰撞体和交互外力测 live 路径；这只是性能与物理测试，不要另造一套人物动作成品。后续仍须回到权威人物 / 动作系统做穿着验收。

### 12.3 目标与底线

目标为声明的目标设备上实现稳定 60 FPS 的交互体验；60 Hz 的帧周期约为 16.67ms。设备未确认之前，这只是目标，不是适用于所有电脑的保证。

建议初始帧时间门槛：热运行 p95 不高于 16.67ms，p99 和卡顿峰值单列；若采用其他门槛必须明确说明。物理单独核对时间：固定输入下持续推进，`simulationSeconds / activeWallSeconds` 在允许的时钟量化误差内接近 1，不能靠小于 1 的慢动作过关。暂停、后台标签和设备失去上下文的时段单独记录，不混入普通运行统计。

结构与物理质量门槛先在 S0 建立：同一时刻同一输入比较控制点位移误差、速度、缝合间隙、最大应变、人体 / 衣物接触，以及画面轮廓误差。数字容差根据当前尺度、材料和用户近看要求标定；本文不编造一个统一毫米数当作已经达成。

必须同时达到“在规定场景无可见穿模”和可解释的数值接触检查。只有稀疏样本距离正常，不足以证明整个衣服都不穿；需要密集离线核验或更完整检测作为补充。不能只保留一个轻量审计再宣称严格保证。

为排除优化仅掩盖显示卡顿，必须对照：物理关闭、live 物理开启、冻结同一真实物理状态仅测显示三个条件。第三个只用于拆分测量，不能作为最终运行模式替代实时物理。

### 12.4 消融测试

分别开关：重复结果整理消除、静态人体更新跳过、buffer 复用、时钟修正、收敛停止、连续需求调度、按需生成、连续几何采样。每次只改变一个因素，再测组合效果。

报告某项优化的绝对耗时差、误差变化和峰值内存，不能只报一个总倍数。若最重成本仍在必须执行的碰撞 / 基础求解，明确指出；连续函数不可能凭空免掉这部分工作。

## 13. 约束、风险与不能快速实现的部分

**最短见效路线不是从零写 GPU 布料。** 现有输出重复、静态数据传输、隐藏显示更新与时钟问题有具体修改位置；能节省多少必须测量。完整碰撞优化和无级真纱线采样则需要数值与视觉测试，不能承诺只是几行 shader 就能全部完成。

**严格连续的需求不等于所有任务数学连续。** 三角形数、任务和资源页是离散的。工程目标是让这些离散操作的可见影响处于误差范围内，并以平滑过渡避免突变；不是把一个无限精度函数存进有限显存。

**不能同时无条件保证任意硬件、无限数量、无限近看和恒定帧率。** 必须声明支持的观察尺度、同屏角色量、材质复杂度、内存和目标设备。若用户进一步要求所有可见纱线永远保持完全相同采样数，仍可做管线 / 求解 / 剔除 / 驻留优化，但渲染成本的可降空间会减少。

**突发靠近不保证零等待。** 网络、生成与上传都有成本；预取和常驻最低合格表示可以减轻突刺，但无法对任意瞬移和极慢网络承诺首帧已是最高精度。未就绪时保留同一编织的当前有效表示，不用缺失块或材质替换掩饰。

**局部求解和连续采样都有接缝风险。** 物理邻接传播、接触对、管截面和跨片块过渡必须专项处理。不能只在一块平布测试成功就推广全部服装。

**现有 WASM / 材料绑定属于资产。** 新 GPU 后端需要同时保住纱线形变、法线、阴影、数值尺度和回退路径；外观已基本认可时，全面更换渲染器的回归成本尤其需要计算。

**本轮不做动作缓存，不等于禁止运行状态。** 当前位置、速度、上一时刻状态、接触记录、静态拓扑、资源缓存、着色器程序缓存是实时系统正常组成；禁止的是以预先录好的服装动作序列替代本轮 live 物理优化。相同参数下有效的初始状态可保留，但不能被包装成任意动作的实时求解能力。

## 16. 外部方法与 API 参考

只作为算法 / API 依据，不作为本工作台的性能证明。查阅日期：2026-10-14。

[R01] Macklin、Müller、Chentanez，*XPBD: Position-Based Simulation of Compliant Constrained Dynamics*，2016。用于约束柔顺性、时间步缩放与约束乘子的依据。本文提出的局部调度与验收门槛不是该论文对 MP05 的验证结果。

[R02] Macklin 等，*Small Steps in Physics Simulation*，2019。用于研究子步和约束迭代的权衡；不得把论文场景的速度或精度数值写成 MP05 测试成绩。

[R03] Three.js 官方，*WebGPURenderer* 迁移说明。用于确认现有 GLSL / onBeforeCompile 路径迁移的工作范围。

[R04] MDN，*WebGPU API* 与 *GPUBuffer*。用于设备、缓冲区、计算 / 渲染管线与读回机制。端到端避免全量往返是本方案的工程目标，不是 GPU 加速幅度保证。

[R05] W3C，*WebGPU Shading Language*。用于核对数值类型、存储与同步约束；实现时锁定实际浏览器和 Three.js 版本。

[R06] MDN，*SharedArrayBuffer*。用于核对共享内存的安全上下文与跨源隔离前提；本方案不要求先使用共享内存。

[R07] MDN，*EXT_disjoint_timer_query*。用于区分 GPU 计时与主线程提交计时；WebGL 版本和扩展可用性需实际查询，不支持时报告未测量。
