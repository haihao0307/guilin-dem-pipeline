# GitHub 现有动物工作台审计与螃蟹生产线取舍

## 审计范围

本轮重点读取了以下现有分支与工程：

1. `work/kaopu-bird-triad-r01-20260929`
2. `work/kaopu-fish-muskellunge-r01-20260930`
3. `work/kaopu-fish-muskellunge-surface-r02-20260930`
4. `work/kaopu-mammal-r06-cat-dog-integration-20260930`
5. 其中的早期 `kaopu-animal-r03`、四足 R04/R05 结构

审计目标不是挑一个动物工程直接改名为 Crab，而是判断哪些属于长期公共生产方法，哪些只是某个对象的临时做法。

## 1. 鸟类三系统：工程组织可继承

鸟类线已经把工作台、构建证据、公开发布证明和谱／乐器分离作为独立结构保存。螃蟹线继承这种“可验证工程交付”，但不继承鸟类的体轴、羽毛、翼面或飞行动作。

## 2. 鱼类 R01：三系统关系正确，静态造形路线后来被否定

鱼类 R01 的优点：

- Composer 读取证据、冻结来源并编译 Base + Source Score；
- Resolved Score 显式保存对象参数；
- Instrument 只提供鱼类公共运算；
- 老师模型被排除在正式运行时之外；
- 可以独立重演、测量和生成指纹。

但 R01 的鱼体以少量人工截面为核心，并另外生成眼、嘴、牙和鳍。后续 R02 已正式判定：这不等于从模型完整表面进行参数化重构。

所以螃蟹线只继承 R01 的三系统和证据链，不继承它的稀疏截面造形方法。

## 3. 鱼类 R02：本项目最重要的静态形体硬门

R02 明确要求：

- 完整读取老师的顶点、三角连接、法线、UV 和表面连接关系；
- 将每一个表面区域拟合为连续参数曲面；
- 对全部采样点报告位置与法线误差；
- 禁止执行者自行补出眼、嘴、鳍等结构；
- 静态形体未验收前禁止绑骨和动作。

螃蟹比鱼拥有更多附肢、分节、遮挡和左右差异，因此这条门只能更严格，不能放松。

## 4. 猫狗 R06：谱／乐器边界最接近本项目目标

R06 已明确：

- 乐器只放多种对象真正共用的计算；
- 尺度、比例、关节、耳、尾、材质等对象差异归外部谱；
- 纯乐器零身份预设、零示例谱；
- 空播放器在没有外部谱时不产生动物；
- 老师可被测量，但不得作为运行时几何存活。

螃蟹线完整继承这一边界。

## 5. 早期 Animal K3：保留工程经验，淘汰身份分发

K3 的优点是纯生成库、空播放器和离线重演；问题是短谱中的 B／E／T 标签仍会选择乐器里的熊、鹰、龟原型。它适合展示参数化原型，却不适合作为“拿到一份全新谱就从头演奏一个新对象”的最终母本。

螃蟹乐器因此禁止 `speciesPreset`、`crabType` 或名称查表来选择完成形。

## 6. 螃蟹领域与鱼／哺乳动物不同的结构

螃蟹不能套用鱼类连续躯干或哺乳动物软组织四足：

- 主体是多块刚性外骨骼区域，而不是一张随骨骼大幅形变的软皮；
- 十足目附肢是明确的分节链，每一段几何和关节轴都必须由谱表达；
- 左右通常近似成对，但螯足可能明显不对称，不能强制全局镜像；
- 足端接触、横向行走和相位耦合需要独立的蟹行求解；
- 眼柄、触角、口器和刚毛不能作为装饰性小件随便补上；
- 背甲上表面、侧缘、腹面和被腿遮挡区域都必须纳入完整表面证据。

因此新乐器的核心不是“造一只螃蟹”，而是提供：表面图表拼合、刚性区域、谱定义分节链、受限关节、螯钳、足端接触和外骨骼微形态这些公共声部。

## 7. 当前结论

新分支以 Fish Surface R02 为底，是为了继承最严格的完整表面纪律；同时把 Mammal R06 的零预设边界和 Fish R01 的 Composer／Score／Instrument 工程组织写入新项目。

第一只老师未冻结之前，工程只建立契约与空白工作台，不生成临时螃蟹。这不是停工，而是避免从第一步就把错误形体写死进乐器。
