Date: 2026-09-26 (Asia/Shanghai)

## Bounded question

Can a machine-readable scope contract distinguish the authorized one-object Coral method demo from the unauthorized R02 expansion to 19 instances and procedural pore structures, without treating every parameter edit as a new task?

## 2. External method and primary evidence

NASA's Systems Engineering Handbook defines a baseline as an agreed and documented description of attributes to which changes are addressed. Its configuration-change process requires systematic proposal, justification, evaluation, approval, implementation and verification. Its requirements-creep section specifically warns that apparently innocent changes may be enhancements in disguise and calls for formal channels plus impact assessment before approval.

NIST SP 800-53 Rev. 5 control CM-3 requires organizations to determine which changes are controlled, review and approve/disapprove proposed controlled changes, document decisions, implement approved changes, retain records, and monitor the change activity. The official OSCAL catalog makes those control statements machine-readable.

Sources:

- NASA Systems Engineering Handbook, sections 6.2 and 6.5: https://www.nasa.gov/reference/6-0-crosscutting-technical-management/
- NIST SP 800-53 Rev. 5 publication: https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final
- NIST official OSCAL catalog, tag v1.4.0: https://github.com/usnistgov/oscal-content/blob/v1.4.0/nist.gov/SP800-53/rev5/json/NIST_SP-800-53_rev5_catalog-min.json

The transferable method is only the baseline/change-control pattern. KAOPU does not adopt NASA or NIST wholesale.

## 3. Comparison with current KAOPU rules

Current R2 already freezes Task Anchor fields including taskId, targetObject, referenceSet, protectedInvariants and forbiddenRoutes. `scope_expansion` is already forbidden. `MOTHER-NO-METHOD-INVENTION-001` already rejects unrequested method/direction changes, and the reference gate rejects creative substitutes. `TERRAIN-NO-STALE-DELIVERY-001` supplies applicable freshness logic for the overwritten R01 directory entry.

This cycle therefore records no novelty for “freeze scope,” “ask before changing direction,” or “do not serve stale artifacts.” The gap is machine execution: there is no explicit object-cardinality range, visible-feature allow/deny inventory, candidate class, or canonical scope digest to compare against the observed candidate.

## 4. Falsifiable hypothesis

If a Task Anchor freezes:

- `candidateClass` (`METHOD_DEMO_CANDIDATE` versus `PRODUCTION_CANDIDATE`),
- immutable reference digests,
- visible object-count bounds,
- allowed and forbidden visible feature types,
- `authorizationId`, and
- canonical `scopeContractDigest`,

then a pre-promotion verifier will HOLD R02 while admitting a reconstructed R01 scope and a separately reauthorized expansion control. If the gate cannot make all three distinctions, reject the Candidate.

Passing `SCOPE_AUTHORIZED` means only “the candidate stayed inside this scope contract.” It does not prove fidelity, biology, visual quality, production readiness or user acceptance.

## 6. Applicability boundary

Apply only when visible semantic scope can be inventoried reliably. Ordinary parameter changes inside frozen object-count, feature, reference and class bounds do not require a new task. A semantic expansion does.

For generated geometry, the observed inventory must be derived from source/runtime evidence and independently checked; a producer-authored receipt alone is insufficient. Unknown inventory remains UNKNOWN, not PASS.
