# KAOPU Learning Log — Houdini cooked-geometry semantic receipt H03

## Question

How should H01/H02 compare cooked Houdini geometry without falsely treating a raw file hash, point order, bounding box or element counts as semantic geometry identity?

## Evidence and bounded method

SideFX Houdini 22.0 documentation was locked for points versus vertices, primitives, owner-specific attributes, groups, HOM geometry/attribute metadata and floating-point reproducibility. A synthetic polygon CPU fixture then tested thirteen counterexamples. No Houdini executable, production asset or Mother branch was used.

All thirteen checks passed. A stable-ID receipt ignored harmless point/primitive enumeration changes, cyclic polygon start changes and unordered-group enumeration, while a naive serialization hash changed. The same bounding box and point/primitive counts admitted a different diagonal topology. Vertex-owned UV, face winding, detail metadata, group membership and numeric storage precision each changed the semantic receipt.

## Observation

- Houdini distinguishes points, vertices and primitives: coincident positions do not prove identical point sharing or topology.
- Attribute owner is semantic. A vertex UV is not interchangeable with a point UV, and the schema must retain type, precision, tuple size and qualifier.
- Ordered and unordered groups have different contracts.
- SideFX's `id` convention is distinct from element number and exists specifically to survive number changes.
- Geometry data IDs and counters are change-tracking aids; they are not substituted for an explicit content receipt.
- Cross-machine exact floating-point reproduction remains a separate runtime question.

## Candidate

Use three separate cooked-output records:

1. Exact transport hash for the emitted geometry file or byte stream.
2. Conservative semantic geometry receipt over coordinate frame/units, stable point and primitive IDs, topology and winding, owner-specific typed attribute schemas and values, detail attributes, and group names/order/membership.
3. Quality and acceptance metrics such as counts, bounds, area, volume, normals or tolerances.

For polygon cycles, normalize only the choice of starting corner. Do not normalize reversal, because winding can affect orientation. Sort only semantically unordered collections. Reject missing or duplicate stable IDs rather than guessing correspondence from position, especially with coincident points.

## Current Best View

H01/H02 provenance hashes identify recipe and definition inputs; a cooked-geometry receipt must separately bind the actual semantic output. Raw bytes are too strict for semantic comparison, while bbox/counts are too weak. Stable IDs plus owner-aware topology and attributes provide a bounded conservative middle layer.

## Rejected

- “Same bounding box and element counts means the same geometry.”
- “Hashing point positions in current point-number order is a stable semantic identity.”
- “Point and vertex attributes are interchangeable if values look alike.”
- “A cyclic polygon start change and a winding reversal are both harmless reorderings.”
- “Houdini data IDs or modification counters are content hashes.”
- “One semantic receipt can also stand in for visual, physical or human acceptance.”

## Unknown

- Actual HOM extraction and cooked BGeo/Geo transport were not executed.
- Stable semantic IDs may be absent, duplicated or regenerated by real networks.
- Packed primitives, volumes, curves, NURBS, polygon soups, instancing and USD need type-specific receipts; H03 covers only a polygonal subset.
- Cross-version and cross-machine floating-point equality remains unverified.
- Renderer equivalence, collision behavior and human acceptance remain separate.
