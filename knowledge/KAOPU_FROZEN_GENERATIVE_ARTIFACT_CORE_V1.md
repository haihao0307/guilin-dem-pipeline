# KAOPU 冻结生成资产核心协议 V1

日期：2026-09-19  
状态：用户确认的跨 Mother 核心原则  
维护角色：小猫 / KAOPU 协调层  
性质：协调合同，不是任何一条生产线的代写实现

## 1. 核心结论

高质量程序化对象允许在生产阶段花很长时间生成；一旦种子、参数、输入真值和质量合同通过人工验收，就把结果冻结成正式资产。正式运行时直接加载冻结资产，不再重复生成。

```text
慢速高质量生成
→ 人工检查与接受
→ 冻结几何 / 材质 / 碰撞 / 行为基础数据
→ 计算身份哈希
→ 上传 GitHub / CDN
→ 运行时直接加载
→ 浏览器本地缓存作为二级加速
```

这套方法解决的不是“把算法做简单”，而是把昂贵计算从观看阶段搬到生产阶段：

```text
质量第一
生产可以慢
正式打开必须快
结果必须可追溯、可复现、不可静默漂移
```

## 2. 一个种子不是完整身份

“同一个种子”只有在生成器、参数、输入和质量完全相同时，才代表同一个对象。正式身份必须至少包含：

```text
GeneratorVersion
+ SeedDNA
+ ParameterDNA
+ SourceTruthHash
+ CoordinateAndScaleContract
+ QualityContract
```

把上述内容按键排序、单位统一、数值规范化后编码成 canonical JSON，再计算：

```text
ArtifactID = SHA256(canonicalGenerationIdentity)
```

只要 ArtifactID 未改变，系统就不得重新生成正式对象；只应读取已冻结产物。

## 3. 每个对象同时保留两种状态

### 3.1 生成态 Authoring State

用于解释和重建对象：

- 生成器版本；
- 主种子和分层种子；
- 参数 DNA；
- 输入真值及其哈希；
- 坐标系、单位和范围；
- 质量合同；
- 生成环境身份；
- 父版本与变更说明。

### 3.2 冻结态 Frozen Runtime Artifact

用于正式打开和运行：

- 几何二进制；
- 材质参数或纹理；
- 碰撞 / 导航 / 浮力等需要的派生数据；
- 边界、尺度、坐标系；
- 文件大小和 SHA-256；
- ArtifactID；
- 人工验收状态；
- 运行时兼容信息。

只保存最终网格会失去生成来历；只保存函数与种子会导致每次重算。KAOPU 要求两者同时存在。

## 4. Seed DNA 分层规则

一个对象可以对外显示一个主种子，但内部必须把不同职责隔离：

```text
master
├─ shape
├─ structure
├─ damage
├─ cavity / pore
├─ material / color
├─ water / wetness
├─ weather
├─ inclusion / biology
├─ animation / behavior（适用时）
└─ detail
```

规则：

- 改颜色种子不能改变几何；
- 改湿润种子不能改变洞穴或裂缝位置；
- 改微细节不能改变宏观轮廓；
- 改动作或行为种子不能改写角色身体身份；
- 同一完整 Seed DNA 与参数必须得到同一候选身份；
- 接受后的结果以冻结资产为正式真值，不要求终端设备重新浮点复现。

## 5. 游戏时间尺度冻结规则

自然对象在极长时间尺度上会变化，但产品只需处理游戏或工作台覆盖的时间尺度。

如果在产品时间范围内宏观变化不可感知，则可把它定义为静态世界真值：

- 山体大形、岩层、洞穴和主要裂缝；
- 岛屿、礁盘、海床和岸线基础；
- 奇石、砖石、建筑构件；
- 珊瑚礁盘的基础形体；
- 鱼、鸟、猪、人物等生物的身体母体。

动态层必须与冻结身份分离：

- 海浪、潮汐、泡沫；
- 天气、云、风；
- 湿润、苔藓和季节状态；
- 动作、行为和动画相位；
- 少量明确设计的落石、崩塌或破坏事件。

因此，“山在游戏时间内不变”是合法的产品时间尺度定义，不等于宣称地质上永远不变。

## 6. 正式生产生命周期

### G0 输入冻结

固定来源、真值、尺度、坐标系和不可修改项。

### G1 候选生成

可以使用高成本、高分辨率、多小时甚至多日计算；允许批量搜索种子。

### G2 结构与视觉检查

检查：

- 宏观形体；
- 中尺度关系；
- 近景细节；
- 颜色、粗糙度、法线与形体是否同因关联；
- 物理、碰撞和行为是否一致；
- 是否出现算法伪影、周期接缝、穿模或错误构造。

### G3 人工接受

只有用户或被授权的人工验收可以把 `visualAcceptance` 设为 true。测试通过不能代替人工接受。

### G4 冻结导出

生成正式几何、材质、碰撞等产物；写入 manifest；逐文件计算 SHA-256。

### G5 发布

把冻结产物放到固定 GitHub 提交或 CDN，不依赖开发机临时缓存。

### G6 运行加载

正式页面先读取 manifest，再按 ArtifactID 获取冻结产物。正式运行不得默认调用生成器。

### G7 本地二级缓存

浏览器可用 Cache Storage 或 IndexedDB 保存已下载产物。缓存丢失时重新下载官方冻结产物，而不是重新生成。

### G8 明确修订

算法、参数、真值或质量发生改变时，生成新的 ArtifactID 和新版本；旧的已接受产物不得被静默覆盖。

## 7. 权威层级

运行时查找顺序：

```text
1. 固定提交 / CDN 上的权威冻结产物
2. 浏览器本地校验通过的同 ArtifactID 缓存
3. 作者模式中的生成器（只用于缺失候选或明确重建）
```

浏览器缓存不是正式真值，因为它可能被清理、换设备后不存在，也可能被浏览器回收。

## 8. 有限世界原则

项目实际使用的正式对象是有限集合，因此可以用高成本生产换取高质量运行：

- 温州完整区域可以离线生成十小时或更久；
- Stone Money Island 只需要有限数量的岛、礁盘、洞穴、珊瑚和颜色身份；
- 每座山、每块奇石可以拥有独立 ArtifactID；
- 每种鱼、鸟、动物、NPC 可以先慢速生成母体，再冻结身体和材质；
- 砖、瓦、墙和建筑构件可以冻结已接受母体，并从母体派生有限实例。

不是为了实时随机而永久降低质量；而是生产时充分计算，运行时读取确定结果。

## 9. 文件和目录建议

每个正式对象建议使用：

```text
objects/<object-id>/
  artifact.manifest.json
  source.recipe.json
  geometry.bin
  material.bin or material.json
  collision.bin            # 如需要
  preview/                  # 内部 QA，可选
  provenance.md
```

manifest 至少记录：

- schemaVersion；
- objectId；
- artifactId；
- parentArtifactId；
- generatorVersion；
- seedDNA；
- parameterDNAHash；
- sourceTruthHash；
- coordinateSystem；
- unitScale；
- qualityContract；
- files、bytes、sha256；
- visualAcceptance；
- productionReady；
- acceptedBy、acceptedAt；
- immutable；
- runtimeCompatibility。

## 10. 性能优化优先级

不得把“优化”解释为另做一个低质量版本。正确顺序：

1. 先冻结已接受的高质量产物；
2. 运行时不重算；
3. 使用紧凑二进制、索引复用、量化与无损/可控压缩；
4. CDN 与 HTTP 缓存；
5. 浏览器本地缓存；
6. 按需加载和空间分块；
7. 静止时停止无意义重绘；
8. 只有作者模式才使用 Worker 重新生成。

任何压缩或分块不得改变 ArtifactID 所代表的可见和结构身份；若改变，必须产生新版本。

## 11. 跨 Mother 边界

小猫 / KAOPU 协调层负责：

- 维护本合同；
- 统一 manifest 和 ArtifactID 规则；
- 检查各 Mother 是否正确采用；
- 记录边界、失败和可复用方法；
- 不替任何 Mother 写其生产实现。

每个 Mother 负责：

- 自己领域的真值与生成器；
- 自己的种子分层；
- 自己的候选生成、视觉验收和冻结导出；
- 自己的性能、浏览器和物理检查；
- 向协调层回传 manifest 与 adoption receipt。

Brick Mother 只实现砖、土砖、石材、墙体等 Brick 体系；Landscape、Ocean、Fish、Bird 等由各自 Mother 执行。本合同只传递工作模式，不跨边界代写生产代码。

## 12. 禁止项

- 只用一个整数种子作为正式缓存键；
- 每次打开正式页面都重新生成；
- 把浏览器缓存当唯一正式资产；
- 新算法静默覆盖已接受对象；
- 为了打开快而偷偷降低形体或材质质量；
- 混淆静态身份和动态状态；
- 用截图或概念图代替真实冻结资产；
- 测试通过后自动写 `visualAcceptance=true`；
- 一个 Mother 越界替另一个 Mother 实施其生产代码。

## 13. 一句话原则

> 种子与配方负责可重建，冻结产物负责快速打开，哈希与版本负责防止漂移，人工验收负责决定什么可以成为世界真值。
